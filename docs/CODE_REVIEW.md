# 代码审查标准与流程（CODE_REVIEW）

> 适用项目：LiquidGlassWatermark（液态玻璃水印 Android App）
> 生效版本：v15.23 起
> 维护人：代码审查专家（Code Reviewer）
> 定位：本文件是**强制规范**，不是建议。任何合并进主干（`app/src/main`）的改动都必须走完本流程。

---

## 一、为什么需要这份文件

本项目的核心矛盾是 **画质 / 帧率 / 速度三者都不许妥协**，而实现它的代码集中在
GPU 硬解硬编（`GpuMp4Exporter`）、CPU 逐帧兜底（`Mp4Exporter`）、动图量化
（`GifEncoder` / `GifQuant`）、多级解码（`MotionDecoder`）四条高风险路径上。
这些路径的共同特征是：

- **静默失败**：渲染错了不抛异常，只是画面对了 99%，剩下 1% 是绿幕/黑边/噪点。
- **性能回归无感**：多一次位图分配，单帧多 3ms，10 万帧就是 5 分钟，但功能测试全绿。
- **兜底掩盖缺陷**：CPU 回退路径让"GPU 出问题"表现成"导出很慢"而不是"导出失败"。

因此本项目的审查重点**不是代码风格**，而是：**行为等价性、资源生命周期、兜底逻辑的真实触发条件、以及画质数值的可验证性**。

## 二、审查清单（按严重度分级）

### 🔴 Blocker（必须修复，否则不予交付）

| # | 检查项 | 判定标准 | 本项目典型反例 |
|---|---|---|---|
| B1 | **画质降级** | 任何以降低分辨率 / 码率 / 采样率 / 帧率换取速度的改动 | 曾提议"导出降到 720p 提速"——**绝对禁止** |
| B2 | **静默吞异常** | `runCatching{}` / `catch(Exception){}` 内部无日志、无返回值语义，调用方无法感知失败 | `runCatching { tmpOut?.delete() }` 可接受（清理无副作用）；`runCatching { decode() }` 不可接受 |
| B3 | **兜底逻辑不可达/恒真** | 兜底分支的条件在生产参数下永远为真（等于没有兜底），或永远为假（等于死代码） | `cpuWatermark` 恒为 `true`，`!cpuWatermark` 分支即死代码 |
| B4 | **资源泄漏** | `Bitmap.recycle()` / `MediaCodec.stop+release` / `Surface.release` / `Extractor.release` 未在 `finally` 中成对出现 | `MotionDecoder` 多级解码任一级抛异常，上层 codec 未释放 |
| B5 | **API 级别越界** | `minSdk = 26`，任何 API 27+ 调用必须有 `Build.VERSION.SDK_INT` 守卫或 `@RequiresApi` | `getScaledFrameAtTime`（API27）、`ImageDecoder`（API28）曾在无守卫下直调 |
| B6 | **数据损坏风险** | 输出文件写入中途失败未删除 `.tmp`；muxer 未 `stop()` 就 `release()` | 取消导出必须删 `.tmp`，否则相册出现半成品 |
| B7 | **主线程阻塞** | `MediaCodec` 同步模式、全分辨率位图解码、文件 IO 出现在主线程 | 导出必须在 `Dispatchers.IO` / 独立线程 |
| B8 | **校验器与产物不一致** | 水印验证器（`verifyWatermarkOnOutput`）的判定区域与实际渲染区域不一致 | patch 区域渲染 + 全帧校验 → 恒失败 → 无限回退 |

### 🟡 Suggestion（应当修复，进入待办）

| # | 检查项 | 判定标准 |
|---|---|---|
| S1 | 死代码 | 无调用方的 `fun` / `val` / 分支 / 资源；注释掉的代码块 |
| S2 | 冗余代码 | 同一逻辑存在两处实现（如两套缩放、两套 YUV 转换） |
| S3 | 魔法数字 | 关键参数（码率、帧率、量化级数、超时）硬编码且无注释说明来源 |
| S4 | 状态耦合 | `EditorState` 这类全局可变单例被多线程读写，无同步说明 |
| S5 | 命名误导 | 变量名与真实语义不符（如 `wmRegion` 实际已废弃但仍参与判断） |
| S6 | 缺少关键路径日志 | 导出各阶段无耗时/帧数/校验结果日志，线上问题无法定位 |
| S7 | 重复 IO | 同一文件被多次 `decodeFile` / 多次 `MediaMetadataRetriever` 打开 |

### 💭 Nit（可选）

- 未使用的 `import`
- 缩进/换行不一致（本项目无强制 linter，不阻塞）
- 注释与代码不同步（**但涉及版本修复原因的注释必须同步**，因为它是历史决策的唯一记录）

## 三、必查的五个高危模块

审查时**必须逐条走完**，不允许"看起来没问题"跳过。

### 1. `GpuMp4Exporter.kt` —— GPU 硬解 + 硬编主路径
- 解码器输出 → `captureVideo2d` → CPU 水印 → `uploadBlit` → `drawFrameBlit` → `swapBuffers`，**每一步的失败是否都会导致回退而不是产出坏视频**？
- `maskBBox` 是否与 `verifyWatermarkOnOutput` 的校验区域一致？（B8）
- 帧循环内是否有每帧位图分配？（应在循环外复用缓冲）
- `deadline` / `firstFrameDeadline` 是否会掐断长视频？（视频轨半截 = 播放到一半卡住）
- 取消路径是否删除了 `.tmp`？（B6）

### 2. `Mp4Exporter.kt` —— CPU 逐帧兜底
- `argbToYuv420` 的 BT.601/709 系数与编码器 `color-format` 是否匹配？（不匹配 = 偏色）
- 每帧 `getFrameAtTime` 的 seek 策略是否会导致 O(n²)？（应按 PTS 顺序单向前进）
- 兜底路径的耗时是否会触发用户误判为"卡死"？是否有进度回调？

### 3. `GifEncoder.kt` / `GifQuant` —— 动图量化
- 调色板 `build(maxColors=256)` 的索引 0 是否固定为透明？透明像素是否被误映射到实色？（= 黑光晕）
- `toIndices(dither)`：抖动会放大色带，但在**全局调色板缺中间色**时会把像素推向饱和色 → **满屏彩色噪点**。是否该关抖动？（本项目结论：关）
- 帧延迟计算：`delay = 100 / fps` 的整数截断是否导致帧率漂移？（累积误差）
- 输出尺寸上限是否与"原画质"承诺冲突？（曾从 480 提到 1080）

### 4. `MotionDecoder.kt` —— 多级解码
- 三级降级（系统硬解 → 指定 codec → Retriever）每一级的**退出条件是否明确**？
- `maxEdge` 的降采样是整数步长最近邻：`step = 1` 时是否真正零损失？
- API 27/28 的调用是否有守卫？（B5）
- 多线程 `getScaledFrameAtTime` 是否共用同一个 `MediaMetadataRetriever`？（**不是线程安全的**）

### 5. `WatermarkRenderer.kt` / `WatermarkEditorView.kt` —— 渲染一致性
- 预览、GIF、MP4 三条路径是否**走同一个渲染函数**？（不一致 = 所见非所得）
- `BlurCache` 的 `invalidateKey` 是否在每帧都变？（不变 = 玻璃不刷新，画面静止）
- `skipBackground = true` 时液态玻璃是否还有可见折射？（无背景 = 折射空 = 水印不可见）

## 四、审查流程（六步，缺一不可）

```
① 静态扫描  →  ② 人工精读  →  ③ 问题分级  →  ④ 修复  →  ⑤ 编译+模拟器验证  →  ⑥ 报告归档
```

### ① 静态扫描（自动化，5 分钟）
```bash
# 1. Android Lint（NewApi / 资源泄漏 / 无用资源）
./gradlew :app:lintDebug

# 2. 未使用资源
./gradlew :app:lintDebug --rerun-tasks | grep -i "unused"

# 3. 死代码线索：找出只有定义没有引用的符号
#    （对每个可疑符号，全仓 grep 排除定义行）
grep -rn "funName" app/src/main --include=*.kt | wc -l   # 期望 >= 2
```

**判据**：Lint 的 `Error` 必须清零；`Warning` 必须逐条给出"修 / 不修 + 理由"。

### ② 人工精读（按第三节五个模块，逐模块过清单）

重点不是读懂每一行，而是回答四个问题：
1. 这段代码**什么时候会失败**？
2. 失败后**用户看到什么**？
3. 失败是否**被日志记录下来**？
4. 修复它**会不会降低画质**？（若是 → 换方案，不许降级）

### ③ 问题分级（写入问题清单）
每条问题必须有：**文件:行号 / 分级 / 现象 / 根因 / 修复方案 / 是否影响画质**。

### ④ 修复（一次改一类，改完立即编译）
- 一个 PR / 一次提交只做一类事（修 bug 与删死代码分开）。
- **删代码前必须证明不可达**：给出全仓 grep 结果（引用数为 0 或仅在注释中）。
- **删代码后必须证明行为等价**：说明被删分支的等价路径是哪一条。

### ⑤ 编译 + 模拟器验证（不可跳过）
```bash
./gradlew assembleRelease assembleDebug   # 必须零 error
# 安装 debug 包（包名带 .debug，可与稳定版共存）
adb install -r app/build/outputs/apk/debug/app-debug.apk
```
模拟器上**必须实操**的项（见第五节验收表），不接受"能启动就算通过"。

### ⑥ 报告归档
每次审查产出两份文档，放在交付目录：
- `代码审查报告_vX.XX.md`：问题清单 + 修复明细 + 删除明细
- `验证报告_vX.XX.md`：编译结果 + Lint 对比 + 模拟器实测记录

## 七、本项目的三条铁律

1. **不许用画质换速度。** 提速只能走"更快的等价路径"（GPU 硬解硬编、复用缓冲、减少拷贝），不能走"更少的像素/更低的码率"。
2. **兜底不能掩盖缺陷。** 回退路径存在是为了保交付，不是为了让人忽略主路径的 bug。每次回退都必须打日志，且日志里能看出回退原因。
3. **所见即所得。** 预览、GIF、MP4 必须共用同一套渲染函数。任何"导出时另算一遍"的实现都是 bug 温床。
